# data/real：真实营销场景的脱敏 trace

徐千富，2026-09-28。对应 `docs/MODULES.md` 末尾「分工口径：真实场景与判定规则」的第一项交付（场景的数据）和脱敏规则，也就是 `docs/ARCHITECTURE.md` 输入层里「千富脱敏 trace」那条线。判据见 `docs/CRITERIA.md`，故事见 `docs/STORY.md`。

## 这是什么

某茶饮品牌的小红书评论舆情监控项目（不息，2026 年 9 月一期上线）。线上有一个「评论打标 Agent」：每条新评论连同它所在的笔记、品牌配置（品牌、产品词、好评和差评监控词）一起送给模型，模型判断这条评论对品牌是正向、中性还是负向，负向时再给出负面归因大类（口感、价格、活动规则等）。负向评论进预警和日报。

业务方会在工具里对打错的评论逐条改判，改判记录落在业务库的 `sm_comment_review` 表里。改判后的标签，以及早先业务复核过的金标集，就是这批 trace 的金标来源。

| 文件 | 内容 | 条数 | 通过 / 不通过 |
|---|---|---|---|
| `yuqing_v31_prod.json` | 生产环境 Prompt V3.1 打错、被业务人工改判的评论（2026-09-20 同一轮复核） | 18 | 0 / 18 |
| `yuqing_v38_eval.json` | Prompt V3.8 离线评测（2026-09-22，jev-1.13.0） | 38 | 29 / 9 |

两份文件里，同一条评论的 `sparkjury.task_id` 相同，共 13 条重叠。所以可以直接做 V3.1 到 V3.8 的回归对比：

```bash
uv run sparkjury run --config <v31 的 run 配置>    # inputs 指向 data/real/yuqing_v31_prod.json，source = "otel"
uv run sparkjury run --config <v38 的 run 配置>
uv run sparkjury regress --before runs/<v31>/sparkjury.db --after runs/<v38>/sparkjury.db
```

2026-09-28 用本地 mock 裁判实测的结果是：13 个共同任务 pass^1 从 0% 到 100%，fixed 13、broken 0，三道门禁全部 PASS。降级只有一项，Jev 没配 key 退回本地仲裁。

V3.8 在另外 9 条上判错了，方向和 V3.1 正好相反：业务金标是负向，V3.8 判成中性。见下文「已知局限」。

## 抽样

- **V3.1**：从生产改判导出（60 行，按评论文本去重后 58 条）中，先取与 V3.8 评测重叠的全部 13 条，再给还没覆盖到的人工归因类别各补一条，一共补 5 条。
- **V3.8**：先取上面那 13 条重叠评论，再取业务复核金标里 V3.8 判错的全部 9 条，最后按负面归因大类轮流抽 16 条判对的。随机种子固定为 `20260928`。
- **成功标准**：`sparkjury.success` 等于「模型的情感标签 == 人工标签」。人工标签对 V3.1 来说是生产改判结果；对 V3.8 来说，重叠的 13 条用生产改判，其余用业务复核金标，来源写在 `yuqing.gold_source` 里。

## 格式

格式是 OTLP/JSON，形状对齐 `data/samples/otel_sample.json`，由 `src/sparkjury/adapters/otel.py` 读入。每条 trace 有两个 span。

根 span 是 `invoke_agent yuqing_tagging_agent`，带下面这些属性：

- 适配器会读的：`sparkjury.task_id`、`sparkjury.trial`（都是 0）、`sparkjury.success`、`sparkjury.domain`（值为 `marketing_yuqing`）。
- 只作留痕、适配器不读的：`yuqing.prompt_version`、`yuqing.model_label`、`yuqing.human_label`、`yuqing.gold_source`，以及下面两个：
  - `yuqing.relabel_cause`：只在 V3.1 上有，是 PM 手工归因的类别，比如「抽奖没中」「借楼转卖」。聚类结果可以拿它来对照。
  - `yuqing.negative_point`：只在 V3.8 上有。

子 span 是 `chat <model>`：

- `gen_ai.input.messages`：system 一句话说明任务和 Prompt 版本；user 是一个 JSON，装着笔记、配置、目标评论 ID 和评论串。
- `gen_ai.output.messages`：模型原始回答。V3.8 带每个选项的概率和置信度；V3.1 只有最终标签。
- 还带 token 用量。

这个 Agent 本来就是单次判别调用，**没有工具步骤**，所以 trace 里没有 `execute_tool` span，也不应该伪造。

## 脱敏规则

原则是：评论原文保留，因为那是被评的对象，去掉就不叫真实 trace 了；能指向具体客户、具体个人、具体记录的东西，一律删除或替换。

| 字段 / 内容 | 处理 | 理由 |
|---|---|---|
| 品牌名（含简称、昵称、英文写法、话题标签里的） | 替换为「品牌A」 | 客户身份 |
| 产品名、周边名 | 替换为「产品A1」到「产品A17」、「周边A1」 | 产品线能反推客户 |
| 联名方、联名方主理人、代言人 | 替换为「联名方C」「联名方C主理人」「代言人D」 | 能反推客户和档期 |
| 评论里提到的其他品牌 | 替换为「竞品B1」「竞品B2」…… | 不在公开数据里点名第三方品牌 |
| 活动口号、品牌口号 | 替换为「活动口号」「品牌口号」 | 可直接搜到客户 |
| 评论 ID、笔记 ID、数据库主键 | 加盐 sha256，截 12 位，数字位映射成字母 | 保留「同一条评论」的关联，不能反查 |
| 评论作者昵称 | 删除 | 个人信息 |
| 正文里的 `@昵称` | 换成 `@用户` | 个人信息 |
| URL（含 xsec token） | 换成 `[链接已删除]` | 能定位到原帖和账号 |
| 7 位以上连续数字、16 位以上十六进制串 | 换成 `[数字已删除]` / `[ID已删除]` | 防手机号、订单号、平台 ID 漏网 |
| 点赞数、发布时间、评论是否已删除 | 删除 | 与判别无关，且能辅助定位 |
| 请求哈希 `request_sha256` | 删除 | 能和原始请求对上 |
| System Prompt 全文 | 不放，只写版本号 | 业务方资产 |
| 模型概率 | 保留，四舍五入到 4 位小数 | 判别证据；截断只是为了去掉浮点噪声 |
| 时间 | V3.8：该轮评测创建时间加行号，时长是真实耗时。V3.1：人工复核时间 | 原始调用时间没有逐条留存，属性 `yuqing.timestamp_note` 里写明了 |

替换靠一张本地别名表，按「长词先换」执行，免得短词把长词拆坏。别名表本身不进仓库，因为它就是原名对照表。

### 两道检查

1. **自动泄露自检**（脚本内置）：输出前扫描每个 span 除 traceId 和 spanId 以外的全部内容。命中下面任何一项就非零退出、不写文件：
   - 别名表里的任何原名，不区分大小写；
   - URL；
   - 不是 `@用户` 的 @；
   - 7 位以上连续数字；
   - 16 位以上十六进制串。
2. **人工通读**：自检只认得别名表里已有的词。2026-09-28 通读全部评论和笔记正文时，又补进了 13 条别名，包括品牌昵称、两个产品和一个周边的简称、代言人、活动口号与品牌口号、三个第三方品牌。以后换数据要再通读一遍，不能只信自检。

## 什么不出本地

原始数据全部留在导出者本机，不进仓库，也不发给任何云端服务：

- 评测结果 `results.json`
- 生产改判导出 xlsx
- PM 手工归因表
- 别名表
- 哈希盐
- System Prompt 全文
- 评论作者昵称、原始 ID 和 URL

## 复现

读 xlsx 需要 openpyxl，它不在项目依赖里，所以用 `--with` 临时带上：

```bash
uv run --with openpyxl python scripts/export_yuqing_otel.py \
  --v38-results <本地>/jev-v38-negative-20260922/results.json \
  --relabel-xlsx <本地>/Result_6.xlsx \
  --causes <本地>/relabel_causes.json \
  --alias-map <本地>/alias_map.json \
  --salt-file <本地>/salt.txt
```

盐不变、数据不变，输出就逐字节不变。

## 已知局限

- **没有工具调用。** `tool_use` 维度在这个场景里不适用。现有裁判量表按 τ²-bench 客服场景写，mock 裁判给出的 tool_use 满分没有意义。
- **现有量表不是为判别类写的。** outcome 的含义是「标签对不对」，要按 `docs/CRITERIA.md` 的「补充：判别类」来理解。
- **V3.1 缺原始响应。** 生产环境只落了最终标签，没有笔记上下文。所以 V3.1 的 trace 只有评论本身，比 V3.8 那边信息少。
- **两套金标有冲突。** 「多少钱出一张」这类求购、转卖评论，在早先的 V3.3 业务复核金标里算负向；但 9.20 的生产改判把同类评论统一改成了中性。V3.8 那 9 条「判错」里，至少有一部分是被金标冲突冤枉的。这正是聚类加人拍板要处理的情况，不在数据层擅自裁决。
- **样本量小。** 一共 56 条，只够演示链路和讲故事，不够给出统计结论。
