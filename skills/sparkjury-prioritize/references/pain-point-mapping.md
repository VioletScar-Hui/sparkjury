# references/pain-point-mapping.md — 这个 skill 到底解决了谁的什么问题

本文件把本 skill 的每个设计决定，对回到千富公司 PM 的原话痛点上。
写它的目的：防止 skill 变成"为了有而有"的一环 —— 每个机制都应该能回答
**"去掉它，PM 会重新遇到什么麻烦"**。

> 说明：调研报告 §4.3「痛点 4」是本 skill 的立项依据（任务书指定对应条目）。
> 该报告文件**不在本仓库内**，本文件不复述其原文、不引用未经核对的数据，
> 只把痛点表述为可对照的设计问题。要把原报告接入仓库，属 `clarify` 的工作。

## 痛点表述

**PM 的原话痛点**（任务书转述）：
> "归因后不知道先改哪个。"

拆开是三个更具体的问题：

| # | PM 实际卡住的地方 | 本 skill 的对应机制 |
|---|---|---|
| 1 | "失败我看到了，但它们不是一个量级的东西，我没法比" | `severity_max` → `severity_weight` 查表，severity=3 的类天然压过 severity=1 |
| 2 | "哪个影响面大？我没法数" | `frequency_norm` = 类内 badcase 数 / 总数，占比直接来自数据 |
| 3 | "哪个改起来划算？这个我心里有数但说不清，也没法写进文档" | `fixability_boost` 显式建模，且标注是人工先验未经校准 |
| 4 | "就算排出来，我也说不清为什么是这个顺序" | 每条 `rationale` 必须能还原成三个数的乘法 |

**核心设计回应**：痛点不是缺信息，是缺一个**能把三件事乘在一起、且每一步可复算**的顺序。
本 skill 不做"综合评估"——那正是 PM 每天在脑子里做而做不成文档的事。

## 逐条映射

### 映射 1：只推一个 top，而不是一个漂亮的完整排序表

| | |
|---|---|
| **痛点** | PM 拿到排好的全表，依然不知道今天该干什么。十个类的排序表是给分析师看的，不是给排期的人看的 |
| **机制** | `top_recommendation_count = 1`（pack 硬约束）；`top_recommendation` 只一个，附一句 `one_line_reason` |
| **去掉它会怎样** | 卡片变成"建议依次关注 F02/F04/F01/F06…"，PM 的注意力被摊平，最后大概率按自己原本的直觉行事 —— skill 白做 |
| **代价** | 排序表的其余部分仍然输出在 `ranked` 里（工程师侧要看），只是不推 |

这是本 skill 唯一一处**为了用户认知负担而牺牲信息完整性**的决定。
理由：卡片是给 PM 的行动入口，排序表是给工程师的参考，两者的信息粒度本来就该不同。

### 映射 2：rationale 必须可复算

| | |
|---|---|
| **痛点** | PM 排不出顺序的次要原因是：**说不出为什么**。说不清就过不了评审，也传不给团队 |
| **机制** | 每条 rationale 写成 `frequency_norm=0.2000 (12/60) × severity_weight=1.0 (severity_max=3) × fixability_boost=0.8 (F04) = 0.1600` |
| **去掉它会怎样** | 输出变成"综合评估优先修复 F04"。PM 无法向任何人解释，只能选择信或不信 —— 而"不信"会连带否掉整个 skill |
| **代价** | rationale 变长，证据卡上占地方 |

**为什么强调"可复算"而不是"可解释"**：可解释可以靠自然语言糊过去，
可复算要求任何人拿同样的输入能得出同样的数。本 skill 是确定性计算，无模型调用，
这一点是天然成立的 —— 也正因此，把它做成不可复算是毫无借口的。

### 映射 3：fixability 显式建模，且承认它是先验

| | |
|---|---|
| **痛点** | PM 心里的"哪个好改"是真实存在的判断，但它从不出现在任何评测报告里。于是它要么被忽略（排序失真），要么被偷偷塞进结论（不可审计） |
| **机制** | `fixability_boost` 作为独立因子显式出现；`fixability_source: human_prior_pack_v0.1_uncalibrated` 标注它未经校准；`meta.disclaimer` 写明只表达相对顺序 |
| **去掉它会怎样** | 只剩频率 × 严重度，排出来的顺序会系统性地偏向"难改但显眼"的类（典型如 F08 危险动作） |
| **代价** | 读者可能把先验当结论用 —— 这是本设计最大的风险，所以标注必须强制存在 |

**把这个因子藏起来比没有它更糟**：一个显式的 0.8 可以被挑战、可以被校准、可以被 govern 改掉；
一个隐式的"我觉得"不行。

### 映射 4：黄金池 hook —— PM 的每次拍板都不丢失

| | |
|---|---|
| **痛点** | PM 嘴上说"先修 F06"，报告上写着"先修 F02"。下一次跑 Report，又是一份"先修 F02"。**人校正过的结论没有地方存，于是每天都重新校正一遍** |
| **机制** | 读 ledger 的 `override_priority` 事件，下一轮把 `payload.taxonomy_id` 指定的类提升到人工名次（`to_rank`），rationale 注明来源；匹配不上的事件进 `meta.override_unmatched` 并打 debug 级说明，**不静默丢弃** |
| **去掉它会怎样** | 排序器变成一个每次都给出同样错误建议、每次都被人手动推翻的黑盒 |
| **代价** | 排序结果不再纯粹由公式决定，复算时需要同时读 ledger |

**匹配键是 `taxonomy_id`，不是 `target`**（v0.2 修掉的静默失效）：report 侧
`target = cluster_id`（PM 语义，形如 `C03`），而本 skill 排序表的键是 `category_id`
（形如 `F04`）。v0.1 只用 `target` 匹配，两种 id 形状不同 → PM 在卡上改排序永远
匹配不上、无报错、无 override。`target` 形如 `F\d\d` 时仍走兼容路径（v0.1 遗物）。
细则见 `contracts/cross-skill-interfaces.md` §C。

这一条同时是**长期记忆的雏形**：公式是默认判断，人是校准源。
目前只做"重排 + 标注"，不改权重 —— 按 N=1 的 override 调权重会让结论完全由一个人定。
校准系数需要足够多的决策样本，并走 `govern` 的 pack 变更流程。

### 映射 5：拒排而不是补默认值

| | |
|---|---|
| **痛点** | PM 最恨的不是"不知道"，是**拿到一个看起来确定、其实是凑出来的答案** |
| **机制** | 缺 `severity_weight` / 缺 `fixability_boost` / 分母不可用 → 进 `rejected_candidates` 并说明缺什么 |
| **去掉它会怎样** | 静默补一个默认系数，排序照样输出，PM 照样拿去排期 —— 直到有人发现数据对不上 |
| **代价** | 有些类排不了，卡片会有一块空白 |

**宁可空白，不可造假。** 一个诚实的 `rejected_candidates` 会推着人去补 pack；
一个静默补的默认值只会让错误扩散。

## 不解决的（明确划界）

为了对得起这个痛点,也要说清**这个 skill 不碰什么**：

| PM 可能以为本 skill 给 | 实际不给 | 为什么 |
|---|---|---|
| 修复要几个人天 | 具体工时 | 需要工程上下文，本 skill 只有评测数据 |
| 修完 pass^k 能涨多少 | 收益预估 | 需要 `regress` 多轮数据，当前无样本，**未验证** |
| 改哪一行 prompt / 哪个工具描述 | 技术方案 | 那是上游 agent 维护者的事；本 skill 只归类 |
| 错在第几步 | 步骤定位 | cluster 已划界：当前方法准确率 11-14.2%（Who&When arXiv 2505.00212；TRAIL arXiv 2505.08638） |
| "这个类不用管" | 豁免判断 | 排末位 ≠ 不用管。要不要放过一类是产品决策，属 `report` 卡片的呈现，不是排序器的职权 |

最后一条尤其重要：**排序是相对顺序，不是价值审判**。
一个排在末位的类仍然可能因为合规要求必须先处理。
`report` 出卡时必须给读者这个上下文，否则"prioritize 说不用管"会变成一句被误读的结论。

## 自检

这份映射写完，可以用三个问题检验 skill 有没有长歪：

1. **去掉 `top_recommendation_count=1`**，PM 会重新拿到一份排好但无法行动的全表 → 该留下
2. **去掉 `rationale` 的三因子乘法**，PM 会无法向团队解释这个顺序 → 该留下
3. **去掉 override hook**，PM 的每次拍板都会丢失，下一轮重新错一次 → 该留下

若某个机制回答不了这三个问题中的任何一个，它就该被删掉，而不是留给后人维护。
